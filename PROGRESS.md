- **D4** (raised in Phase 0) tools/state/validate_state.py implements a subset of JSON Schema draft 2020-12 by hand, because ADR-0012 fixed these tools as stdlib-only. It rejects any schema construct it does not implement rather than passing silently, but it is not a conformant validator. Revisit only if the schema needs constructs it lacks.
- **D5** (raised in Phase 1) Player has TWO compositing paths - still-frame when paused, region cutouts when playing - and the chrome silhouette must stay in sync with the region or the uncovered part of the hole shows the desktop. Phase 11 owns this invariant. Retire if wry PR #1762 merges and DirectComposition replaces both.
- **D6** (raised in Phase 1) librqbit has no webseed (BEP-19) support, so Internet Archive torrents will not work through the torrent path. Phase 6's InternetArchiveBackend must resolve to direct HTTP instead. Not a defect, but it constrains how that backend is built.
- **D7** (raised in Phase 1) Integration tests that need a running Tauri app cannot run under cargo test on Windows (ADR-0022): a test binary linking Tauri fails to launch with STATUS_ENTRYPOINT_NOT_FOUND, and the targeted fix is nightly-only. Unit tests are unaffected because logic lives in crates/. Such tests belong in the SPEC.md 12.3 manual plan, or a WebDriver harness later.
- **D8** (raised in Phase 1) tiers.rs treats any non-software DXGI adapter as having hardware decode, and uses >= 2 GB dedicated VRAM as a proxy for 'discrete GPU or strong iGPU'. Both are coarse. Whether a SPECIFIC codec decodes in hardware is only knowable at play time from mpv's hwdec-current, so Phase 8 should feed that back and Phase 21 should revisit the VRAM threshold against real Tier 0/1 hardware.
- **D9** (raised in Phase 2) Rail's roving tabindex sets tabIndex imperatively on the first focusable descendant of each mounted item rather than threading it through the render prop. Correct today because `render` returns caller-owned markup, but it silently does nothing if a card's first focusable element is not its main control. Revisit in Phase 9, when real screens use Rail with more complex cards.
- **D10** (raised in Phase 2) The UI audit (tools/uiaudit) drives the design gallery, not real product screens - those do not exist until Phase 9. Its budgets prove the Rail component holds 60fps, not that any real screen does. Revisit in Phase 9: point the audit at the Home screen too.
- **D11** (raised in Phase 3) The data layer uses runtime-checked sqlx::query() rather than the compile-time-checked query! macros. SPEC.md's tech table gives compile-time checking as the REASON sqlx was chosen ('valuable for a learner'), so this is a deviation the author should rule on. Cost of converting: query! needs literal SQL, so archive.rs's dynamically-built preference query cannot use it at all; SQLite nullability inference is weak, so most columns need `as "col!"` annotations; and it adds sqlx-cli plus a `cargo sqlx prepare` step after every schema change. Benefit: SQL typos fail the build instead of a test. Raised at the end of Phase 3, not decided.

- **D34** (raised in Phase 5) SEARCH IS FOUR TIMES SLOWER COLD. Measured the same day on the same fixture: warm p95 7.1-7.4 ms (three consecutive runs), cold p95 36.8 ms with a max of 131.9 ms, taken straight after 750 MB of index I/O evicted SQLite's page cache. Not a regression - the warm numbers reproduce - but the cold column is what a user meets on the first search after launch, and its MAX already exceeds E1's 80 ms budget on a single query. E1 is a p95 criterion so it survives; it must eventually be measured cold. Phase 21 owns the budget, and subtask 5.7's cold-start re-measurement is the natural place to take the number.
- **D35** (raised in Phase 5) EXACT-TITLE QUERIES PAY FOR THE SEMANTIC HALF THEY DO NOT NEED. The engine runs fusion whenever the exact tier did not fill the page, so typing a film's exact name still costs a query embedding (2.4 ms) plus a vector search (4.2 ms) plus a 50-candidate BM25 scan. That is most of the rise from 7.3 ms to 15.0 ms p95. Deliberate for now - the rest of the page is genuinely useful 'more like this' - but it is the first thing to cut if Tier 0 misses E1. Measure before cutting: the same page is what Phase 18's browsing surfaces will want.
- **D36** (raised in Phase 5) RRF's k=60 IS AN UNMEASURED LITERATURE DEFAULT. crates/search-engine::RRF_K. It cannot be swept yet: E2's fixture is exact titles, which never reach fusion, so every value of k produces identical numbers. The sweep belongs with 5.6's semantic fixture, and this phase has already caught one library default (usearch's ef=64) being wrong for this corpus.
- **D37** (raised in Phase 5) RESOLVED 2026-09-13 (subtask 5.7). The pipeline moved from tools/ingest to crates/catalogue, which is what made it reachable from the application at all, and freshness::refresh_if_stale runs on launch - automatic and silent, by the author's decision. Measured: one launch added 4,604 titles, and a launch with nothing to do reports AlreadyCurrent 260 ms after the frontend paints, costing one HEAD request. TWO BUGS WERE FOUND BY RUNNING IT: the first check is stale without a request so it carried no validator and every launch re-downloaded 216 MB; and recording the validator at the END did not fix it either, because the app exits when its window closes and a refresh takes a minute. It is now recorded after the download and before the load - the only boundary that is wrong in neither direction.
- **D38** (raised in Phase 5) THE LANGUAGE FILTER SPEC.md PHASE 5 NAMES CANNOT BE BUILT. media_items.original_language is NULL on all 2,702,737 rows: the IMDb datasets do not publish it and nothing has ever written the column. So 'in Japanese' is parsed by nothing, and 'like Wong Kar-wai but Korean' cannot constrain by language - it has to hope the embedding carries it. Three sources could fill it: title.akas carries a language per alternative-title row and could be aggregated (free, imprecise; D17 already notes akas language handling is wrong in a related way); AniList publishes it for anime; TMDB publishes original_language for everything but needs the per-user key. Recorded rather than shipped, because a filter that silently matches nothing is worse than an absent one.
- **D39** (raised in Phase 5) REOPENED AND REVERSED 2026-09-22. The 'no reordering' answer was measured with variants built by string concatenation - `format!("{document} {synopsis}")` puts the first 400 characters of the synopsis in the document TWICE, and the plot-first variant duplicated the metadata as well - so every variant kept the metadata head in place and merely added text, which is why everything rose together. document::build_with(doc, Layout) now assembles variants through the PRODUCER'S OWN builder, each part appearing once. Re-measured on two fixture queries: 'plot first' (synopsis_chars 1000, synopsis_first, strip_lead) moves Manchester by the Sea #6 -> #1 on the grief query and #5 -> #3 on the nephew query, lifts A Monster Calls #7 -> #5, and drops every ungraded title. THE ORDER CHANGES, which is the trigger D39 itself set for spending a re-embed. `1000 chars` alone does NOT reorder, so it is the position of the metadata rather than the synopsis budget that does the work. Numbers and the caveat - six-item probes over the contested set, not the catalogue - in docs/eval-results.md.
- **D40** (raised in Phase 5) PARTLY ADDRESSED 2026-09-22. The fixture now carries a sub-kind - 'meaning/known-item' - and `eval search --report` prints MRR and top-10 presence for those two queries BESIDE the headline, which is unchanged at 0.1188 over 8 meaning queries. No graded set was widened and no grade was touched: SPEC.md 10.11 forbids redefining an exit criterion, and a criterion rewritten after seeing its own number is not one. What the split shows: topical six = 0.1584, known-item MRR 0.0000 with 0 of 2 reaching the top 10 - so MRR AGREES with nDCG here rather than rescuing it, and the known-item objection, while correct in principle, is not what is costing E3. Still open: whether to widen the two graded sets, which must only ever be done with films that would have been listed on their merits.
- **D41** (raised in Phase 5) THE REFRESH WATERMARK IS A 13.7-SECOND FULL SCAN. `SELECT MAX(CAST(SUBSTR(e.external_id, 3) AS INTEGER)) FROM external_ids e JOIN media_items m ...` computes the highest IMDb id already held, and the cast defeats every index: 13.68 s over 3.2 million rows, logged as a slow statement on every launch that refreshes. It runs on the background task so it costs no user-visible time today. The fix is to store the watermark rather than derive it - the refresh already knows the highest id it inserted - or to add a generated column carrying the numeric id, which ADR-0032 makes tempting anyway since IMDb ids sort as text.
- **D42** (raised in Phase 5) TWO APP INSTANCES CAN BOTH REFRESH. Nothing configures Tauri's single-instance plugin, so two copies can run, and both will check freshness and both may download. Observed while measuring: an instance that checked before another had committed its validator logged `Refreshed { titles_added: 0 }` immediately after a sibling logged `AlreadyCurrent`. Harmless today - `Job` serialises the load through the database and the second refresh inserts nothing - but it is 216 MB of wasted download and it will matter more when Phase 7 adds a torrent session that genuinely cannot run twice. Single-instance is the one-line fix; it belongs with Phase 20's platform integration, or sooner if anything else needs exclusivity.
- **D43** (raised in Phase 5) A SCREENSHOT CAUGHT A HINT THAT WAS LYING, AND THE CLI COULD NOT HAVE. Every result on 'films directed by Alfred Hitchcock from the 1950s' was labelled 'matched words'. They had not matched words - they came from SearchRepository::by_filters, which reused MatchReason::Keyword because there was no better variant. Fixed by adding MatchReason::Filter and a 'matched your filters' label. The general lesson is recorded here rather than only in the case study: eval prints titles, the UI prints EXPLANATIONS, and an explanation can be wrong while every title is right. Anything else that renders a reason to a user needs looking at the same way.
- **D44** (raised in Phase 5) THE DOWNLOADED ARTEFACT NEVER BECOMES SEARCHABLE ON A CLEAN INSTALL. src-tauri/src/lib.rs:130 only ever VIEWS a prebuilt .usearch at index_path(dir); nothing in the application builds one. crates/catalogue/src/assets.rs:84 offers three downloads - the 313 MB embeddings artefact, the model and the tokenizer - and no index. The only builder is tools/ingest/src/main.rs:1102, a dev tool that does not ship. So a user consents to 346 MB, downloads it, and search stays keyword-only because VectorIndex::view finds no file; the 313 MB is inert. It works on this machine ONLY because data/vector-index-bge-small-en-v1.5-int8.usearch was built by hand on 2026-09-07, which is also why no test and no screenshot caught it - the author's dev box is the one configuration where it works. Subtask 5.9 verified the DOWNLOAD end to end, not that the downloaded thing becomes searchable.
- **D45** (raised in Phase 5) AND BUILDING THE INDEX ON FIRST RUN WOULD NOW FAIL. crates/vector-index/src/lib.rs:173 requires artefact.header.count == ids.len() exactly, but subtask 5.7 made the catalogue refresh itself on every launch (ADR-0030), so the catalogue outgrows the published artefact continuously: 858,170 core ids against 855,703 vectors, 2,467 apart one week after the artefact was cut, and it only grows. VERIFIED that the mapping itself is still sound - all 2,467 new core ids sort AFTER the artefact's last position (id 3242554), so position n still means the same title and the artefact is a strict PREFIX of the catalogue. The invariant that matters is 'prefix', not 'equal', and the guard asserts the wrong one. Same mistake had silently disabled `eval embed --report`, which is fixed: it compares over the artefact's range, reports how far the catalogue has run ahead, and still refuses when the catalogue has FEWER ids, which would mean positions really had shifted. D41 and this are one defect in two places and should be fixed together.
